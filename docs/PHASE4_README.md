# Phase 4: User Registration + `/start`

## What This Phase Does

Phase 4 establishes the **core identity system** for the matchmaker bot. It answers
the most fundamental question: *"Who is this person?"*

Every person who taps **Start** on the Telegram bot gets a row in the `users` database
table. This is the first time our application actually *remembers* someone exists.
Without this phase, nothing else in the roadmap (profiles, matching, messaging,
moderation) can function — they all need a User to reference.

Three things were built:

1. **The User database table** — defines what information we store about each person.
2. **The first Alembic migration** — creates that table inside the running PostgreSQL
   container, with version tracking so we can safely evolve the schema later.
3. **The `/start` command handler** — the Telegram entry point that triggers user
   creation and responds with a welcome message.

---

## Why It's Built This Way

### Why UUIDs instead of auto-increment IDs?

In a privacy-first anonymous platform, sequential IDs (`1, 2, 3...`) are dangerous.
If a malicious user knows they are User #500, they can guess that User #499 and #501
exist and potentially probe the system. UUIDs like `a3f7b2c1-8d4e-...` are random,
unguessable, and give nothing away. The real `telegram_id` is stored but **never
shared** with match partners.

### Why a Repository layer?

The repository (`repository.py`) is the **only** file that writes raw database
queries. The handler never touches SQLAlchemy directly. This matters because:

- If we switch databases, we change one file.
- If we need to add caching, we wrap the repository.
- Testing is easy — we can mock the repository without spinning up Postgres.

### Why a Service layer?

The service (`service.py`) owns the **session lifecycle** — open, commit, rollback,
close. Handlers should never manage transactions. This prevents a common bug where a
handler forgets to commit, or a half-finished transaction leaks across requests.

### Why `get_or_create` instead of just `create`?

Users can (and will) tap `/start` multiple times. If we only had `create`, the second
tap would crash with a unique constraint violation on `telegram_id`. The
`get_or_create` pattern makes `/start` **idempotent** — safe to call any number of
times, always producing the correct result.

### Why a Router aggregation pattern?

As we add more commands (`/search`, `/edit`, `/end`, `/block`, `/report`), each will
have its own handler file with its own `Router`. The aggregated `main_router` in
`router.py` collects them all, so `main.py` only ever registers one router. This
keeps the entry point clean as the bot grows.

## How It's Implemented

### Architecture Flow

```
User taps "Start" in Telegram
        │
        ▼
  Telegram API sends /start update
        │
        ▼
  main.py (Dispatcher receives update)
        │
        ▼
  bot/router.py (routes to correct handler)
        │
        ▼
  bot/handlers/start.py (cmd_start function)
        │
        ▼
  core/users/service.py (register_or_fetch)
        │   ┌─ Opens AsyncSession
        │   ├─ Calls repository.get_or_create()
        │   ├─ Commits on success / Rolls back on error
        │   └─ Returns (user, is_new)
        │
        ▼
  core/users/repository.py (get_or_create)
        │   ┌─ SELECT ... WHERE telegram_id = ?
        │   ├─ If found → return existing user
        │   └─ If not → INSERT new user with UUID
        │
        ▼
  Handler sends response message
        │   ├─ New user → Welcome + prompt to /edit
        │   └─ Returning user → Welcome back + available commands
        ▼
  Done.
```

### File Responsibilities

| File | Layer | Responsibility |
|------|-------|----------------|
| `app/core/users/models.py` | Data | Defines the `users` table schema (UUID, telegram_id, timestamps, etc.) |
| `app/core/users/repository.py` | Data Access | All database queries — `get_by_telegram_id`, `create`, `get_or_create` |
| `app/core/users/service.py` | Business Logic | Manages session lifecycle, calls repository, handles commit/rollback |
| `app/bot/handlers/start.py` | Presentation | Receives Telegram `/start`, calls service, sends response message |
| `app/bot/router.py` | Wiring | Aggregates all handler routers into one for the Dispatcher |
| `app/main.py` | Entry Point | Creates Bot + Dispatcher, registers router, starts long-polling |
| `alembic/versions/..._create_users_table.py` | Migration | The actual `CREATE TABLE` SQL, generated by Alembic autogenerate |

### Database Table: `users`

| Column | Type | Nullable | Purpose |
|--------|------|----------|---------|
| `id` | UUID (PK) | No | Random internal identifier — never exposed to other users |
| `telegram_id` | BigInteger (Unique, Indexed) | No | Real Telegram user ID — stored privately |
| `username` | VARCHAR(255) | Yes | Telegram @username (some users don't have one) |
| `first_name` | VARCHAR(255) | No | Telegram display name |
| `is_banned` | Boolean | No | Moderation flag — banned users can't use the bot |
| `created_at` | Timestamp with TZ | No | When the user first hit /start |
| `updated_at` | Timestamp with TZ | No | Auto-updates on any row change |

### Key Design Decisions

1. **Long-polling for now.** Production will use webhooks (Phase 18), but long-polling
   is simpler for development — no need for a public URL or SSL certificate.

2. **No profile data in the User model.** Profile (gender, age, bio, photos) will live
   in a separate `profiles` table (Phase 5). This keeps the User model focused on
   identity and the Profile model focused on matchmaking attributes.

3. **Logging without PII.** The service logs `telegram_id` for debugging but never
   logs message content, usernames, or any data that could identify the person in
   a data breach.

4. **The migration is reversible.** The auto-generated `downgrade()` function drops
   the index and table cleanly, so we can roll back if something goes wrong.
